# Dimension Requests and Constrained Stage Runs

`cases.py` only generates requests with complete parameters and does not execute large models by default:

```sh
python cases.py --kind llm --batch 1 --seq-len 2048 --dtype fp16 --tp 1 --output LLM.json
python cases.py --kind mla --width 64 --query-rank 16 --content-dim 64 --output-width 64 --dtype fp32 --output MLA.json
python cases.py --kind export --directory exported --output EXPORTED.json
```

LLM uses publicly registered definitions of Llama2-7B/70B, Llama3-70B, and Qwen-72B with all declared layer counts, with prefill/decode separated. The workload is a layer-level performance graph and does not contain numerical weights, embeddings, or generation accuracy. batch/context/dtype/tp are explicit choices for this experiment; a single-layer short-sequence control cannot be called a complete model scale.

MLA records four rows with B={1,4}, S={2048,8192}, H128, latent512, position64; the remaining projection widths/dtype must be explicitly given and listed as experimental choices. 64 tiles, 1MiB per private tile, MAC16×16, and 4×16/8×8/64 shared candidate single column; shared capacity must be given in exact bytes, not treating paper MB as MiB. Request generation does not allocate cache.

The export request reads the real EXPORT/INPUT-SHAPES, records file size and original export node count, and does not load numerical roots or weights. A declared summary is not provenance admission, and file size is not a peak memory estimate. All three entry points must subsequently go through the authoritative workload preflight first; graph construction, compilation, serving, and numerical reference are recorded separately.

`preflight.py --cases CASES.json --index N [--resource-budget JSON] [--build-budget JSON] [--cache-replicas N] [--tiles JSON] --output NEW.json` only calls the formal preflight: exported models use the public onnx_preflight, MLA uses the public mla_preflight, and LLM performance graphs use the public transformer_preflight. MLA's build_budget and the general compilation resource_budget are independent ledgers; LLM passes the complete model/phase/batch/seq_len/layers/dtype/iterations through from that row's workload.params, uses that row's tp as the actual parallelism, and an explicit --resource-budget overrides params.resource_budget, otherwise the row's budget is retained. The output saves the complete result returned by the producer as-is; admitted=true corresponds to admitted/exit 0, false corresponds to budget-refused/exit 2. When parameters are invalid, failed and the original diagnostics are saved. CORE does not copy estimation formulas or trim complete layer counts. reference_mode=inputs only validates root values and cannot substitute for whole-graph numerical validation.

For example, row 0 of an existing LLM.json can be run with `python preflight.py --cases LLM.json --index 0 --resource-budget BUDGET.json --output PREFLIGHT.json`. New scale stages should be executed by scale-run within a shared lock and wait for the current lock-holding window to end; this command does not automatically start graph construction or serving. The budget uses public v1 fields, and the producer returns the complete normalized budget and itemized violations; the example does not pre-fill resource answers.

MLA sharding uses an explicit `--streaming-plan STREAM.json`, where STREAM contains exactly `chunk`, `slots`, `capacity` (bytes), and `cache_mode` (sharded/external). For example, `python preflight.py --cases MLA.json --index 0 --streaming-plan STREAM.json --output STREAM-PLAN.json`. That row must declare fp32; its complete batch/sequence/heads/ranks/width is passed through to the formal `mla_stream_plan` without trimming dimensions. The return status is plan-estimated, and exit 0 only means a static estimate was obtained; the original root_fits and conservative_plan_fits are listed separately, and the conservative upper bound is not treated as compilation/capacity or serving pass. When the old command is used without this option, it still calls the dense/canonical mla_preflight. The stream plan has no host/build/replica budget parameters; mixing old `--resource-budget/--build-budget/--cache-replicas/--tiles` will be rejected; the complete resource_budget for actual graph construction is placed in the parameter JSON described below.

`block.py` connects the formal streaming graph to the ordinary compilation path. `PARAMETERS.json` is the complete keyword object for `mla_stream`, containing all canonical roots, complete dimensions, chunk/slots/cache_mode, dtype/epsilon, and an explicit resource_budget; root names and actual sharding are determined by the public workload API. ADF.json is the caller's real hardware. compute/memories are given in slot order as original paths, without guessing rank/group by name or reordering lists.

The Python configuration entry point is `arch_explorer.archs.block_compilation.block_scene(parameters, *, adf, compute, memories, external_memory=None)`, returning (adf, graph WorkloadSpec, mapping). The preflight entry point remains `arch_explorer.archs.paper_scale.preflight_scale_case`, with a new optional keyword streaming; the rest of the signature is compatible.

```sh
python block.py --parameters PARAMETERS.json --adf ADF.json \
  --compute board/tile0/mac board/tile1/mac \
  --memories board/tile0/sram board/tile1/sram --output block-inputs
archexplorer compile block-inputs/SCENE.json --output BLOCK-COMPILED.json
archexplorer prepare BLOCK-COMPILED.json --output block-request
archexplorer evaluate block-request/COMPILATION-REQUEST.json --output BLOCK-RESULT.json
```

The example path above is a placeholder and must come from the actual ADF/topology; the quantity must be verified against slots by the formal block_mapping. In external mode, additionally provide `--external-memory` with the actual external memory path and hardware that has capacity and routing; transfers, read fences, and workspace are billed along common semantics. The output saves the complete ordinary graph WorkloadSpec, v4 MappingSpec, and SCENE, without copying composition/layout/resource formulas. RESULT's scene-emitted only indicates that composition/mapping returned and was written out; subsequent compile, prepare, and service are evidenced separately. The small shared_memory_hardware is a vector-lane mechanism example; the paper's MAC16×16/64slot/1MiB and explicit external memory candidates are subject to the SIM frozen hardware.

Formal physical candidates can use `python block.py --parameters PARAMETERS.json --hardware HARDWARE-OPTIONS.json --output NEW`. The hardware JSON is passed unchanged to the public `components.api.block_memory_hardware`; the compute/memories slot order and external_memory returned by that factory are passed unchanged to block_mapping, without parsing paths or reordering. `HARDWARE.json` saves the complete original metadata, including candidate, all actual slots, capacity, MAC/SIMT/SFU, clock, dataflow, network declarations, and hardware_accuracy. `--hardware` and `--adf` are mutually exclusive; factory mode does not accept manual path overrides, and custom paths use explicit ADF mode.

The thin Python entry `arch_explorer.archs.block_compilation.block_hardware_scene(parameters, *, hardware)` returns (adf, spec, mapping, metadata). hardware is the actual factory kwargs; the 64tiles/1MiB/MAC16×16 on-chip option explicitly has no root compute/cache or DRAM, and external_bytes=134217728 is another explicit 128MiB external memory candidate. Clock, SIMT/SFU, bandwidth, and latency are uncalibrated experimental choices, and the original metadata is preserved unchanged; hardware declarations and scene-emitted do not represent service or measured accuracy.

In SCALE-INPUTS, the per-line parameters belong to `mla_stream_plan` (including capacity, with no numeric root) and cannot be used directly as composition parameters. The composition PARAMETERS.json must separately contain complete canonical inputs, dtype/epsilon, resource_budget, and only keywords accepted by the formal mla_stream; do not silently delete/modify or zero-fill capacity or missing roots. The original on-chip B4/S8192 root capacity exceeding 64MiB is still required-incomplete; external is an independent configuration and cannot replace the original conclusion. The original plan, cumulative logical bytes, per-slot conservative peak, and actual stages of the four-line two-chunk candidates are saved separately. CORE only wires connections; the scale window is advanced by SIM holding a fixed lock.

Metrics in LLM results separate logical weight_bytes/kv_bytes/root_bytes from materialized_root_bytes, root_python_bytes, and estimated_host_bytes; the performance graph has no numeric weights, and a materialized root of 0 cannot prove that hardware capacity is satisfied. plan.status=mapping-required, replicas/physical_peak_bytes are null; actual placement, replication, and capacity are planned along the existing MappingTemplate/prepare_request. stages preserve formal composition/compile/service boundaries, and graph_executed/service_executed are always false. The compact KV performance graph still does not support the complete numeric root path of compile_graph; precheck success does not change this boundary.

The single-stage executor is `archexplorer scale-run PLAN.json --output-dir NEW_STAGE`, where PLAN contains exactly argv/cwd/wall_seconds/memory_bytes/stage/dimensions/estimate. The caller first saves the authoritative resource estimate, then explicitly executes one stage. stage is preflight/graph/compile/service/reference, with 600s/16GiB as the upper limit, CPU BLAS single-threaded, GPU invisible. All three parties share the fixed `/tmp/archexplorer-paper-scale.lock` non-blocking lock, unaffected by TMPDIR/hostname; when busy, no child process is started, and the lock is held until the managed process group ends; scale execution cannot be added concurrently with SIM/QA.

The runner requires Linux `/proc` and child-subreaper. An independent supervision process inherits the lock and takes over orphaned descendants; the caller's subreaper setting remains unchanged. When there are still running descendants after the main process exits, the stage status is failed, and returncode preserves the main process's actual exit code. Normal exit, non-zero exit, cancellation, exception, and timeout all first clean up same-group descendants, then release the lock. If the termination signal is ineffective, escalate to SIGKILL; on timeout or in-group resource overrun, immediately SIGKILL. If cleanup is not yet confirmed, return cleanup-incomplete; the independent supervision process continues to hold the lock, check, and clean up, and SUPERVISION.json saves subsequent status, which cannot be considered finished.

Each process inherits RLIMIT_AS and RLIMIT_CPU hard limits. The entire managed group shares the wall_seconds deadline, and every 20ms checks the sum of member RSS and cumulative CPU; exceeding memory_bytes or CPU budget terminates the entire group. In-group checks are sampling constraints, and shared pages may be double-counted in RSS; it does not provide kernel cgroup total quotas, nor does it constrain processes that actively escape the group. These limits should be interpreted with the results; sampling peaks cannot be treated as precise host peaks.

RESULT.json contains complete argv/environment/budget/dimensions and precheck records, stage status, wall/RSS/CPU, main process exit code, output size, and original logs. cleanup separately lists confirmation status, termination signal, remaining PIDs, and whether the lock is retained; group_peak_rss_bytes/group_observed_cpu_seconds are in-group observations, max_rss_bytes/child_user_seconds/child_system_seconds are main process wait4 statistics, and reaped_processes saves reaping records. When the supervision process exits abnormally, the caller keeps the lock and performs an emergency group check; the main process exit code that cannot be obtained remains null. Capacity rejection and host memory/time budget failure are different; over-budget results remain incomplete, and subsequent steps first check the specific bottleneck rather than blindly increasing resources for retry. Dimension generation, runner control, or precheck success cannot replace actual graph, compile, or component execution.
