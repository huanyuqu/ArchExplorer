# Instantiating GPUs from Components and Comparing with Original Accel-Sim

To connect new graphs/operators unknown to the core library to existing GPU targets, use [external target execution implementations](operator-implementations.md).
Model graphs, inputs, and numerical references belong to workload/extensions; the GPU provider consumes public execution artifacts and capabilities and does not admit based on model names.
The ViT/CLIP below are existing user scenarios and cannot be used to connect new operators by renaming or disguising them.

To create native components directly in non-GPU scenarios, see [standalone component invocation](standalone-components.md).
Standalone creation, minimal service, and same-process isolation require separate actual evidence and cannot be inferred solely from the GPU behavior comparisons on this page.

The goal of this flow is to compose a GPU from SM/clusters, interconnect, L2 partitions, and DRAM instances in the ADF, with a common framework connecting them, routing transactions, and advancing clocks. `accelsim_components` v1 is the component path, and `accelsim` v1 retains the complete original engine path as an oracle. The provider name alone does not prove componentization; actual transaction boundaries and runtime evidence should be checked.

This page is integrated as the component implementation lands; the new native engine required for execution is provided separately from the public wheel. Successful construction and preparation do not mean the native differential passes; after running, the public comparison report must be checked.

## Input and Execution Boundaries

First read the user's ADF file, then the workload and mapping. The ADF is a description of component instances, parameters, and connections, not a GPU class that must be inherited. Components own cache, issue, queue, and controller mechanisms; the framework owns transaction ownership, port routing, clock phases, and lifecycle. The specific native configuration is generated by the component package's public construction interface and is not duplicated in user scripts.

Both sides consume the same new component engine manifest and respectively select component mode and the retained original cycle mode. The complete input includes the engine manifest, component parameters/connections, workload, mapping, program or trace, and their sources. Both sides output to independent new directories, saving the original commands and execution artifacts. The component path runs first, then produces oracle results, avoiding filling statistics from ready-made oracle outputs; the equivalence of common inputs is still verified by the common comparator.

Small ViT and CLIP use the complete forward structure. CLIP includes vision/text dual towers, projection, normalization, and final output; the two mappings must correspond to real program partitioning or execution geometry, not just changed labels. The dynamic instruction/address streams generated by reference execution are synthetic reference traces, not CUDA traces collected from official frameworks, and do not contain real weights.

The trace fixes the instruction, address, and synchronization streams. When changing data dependency paths, address generation, or synchronization semantics, inputs should be re-prepared; the same trace cannot be arbitrarily extrapolated to all new architectures. Componentized comparison only shows that covered software behavior is consistent, not hardware accuracy.

## Preparation and Actual Execution

Install matching versions of libraries and independent native build artifacts; the public wheel does not carry third-party source code, native binaries, or traces. Native simulation runs on the CPU and does not require enabling GPU measurement or downloading weights.

Execute from the [user example directory](../examples/gpu_instantiation/README.md):

```sh
python workflow.py create --model vit --engine /ABS/NEW/engine.json --output cases/vit.json
python workflow.py topology cases/vit.json --output cases/vit-topology.tsv
python workflow.py run cases/vit.json --output runs/vit
python workflow.py replay runs/vit --output replay-vit.json
```

CLIP uses `--model clip` and another set of new output paths. Each case includes two real program mappings with 32 and 64 threads/block; the helper first prepares and evaluates the full set on both sides, then sequentially calls the common `demo` interface to execute, and finally calls the component package's comparator. You can save the candidate/oracle objects from `case.json` separately as scene JSON, using `archexplorer demo prepare --specs scene.json --output ...` and `archexplorer demo run ...`. After these two common commands succeed, the comparator must still be called; they themselves do not claim that the two paths are equal.

Common Python construction and connection interface:

```python
from arch_explorer.archs.gpu_instantiation import case_specs
from arch_explorer.components.accelsim.componentization import gpu_adf, compile_topology

adf = gpu_adf(sm_clusters=4, memory_partitions=8, l2_subpartitions=2)
topology = compile_topology(adf)
case = case_specs('vit', engine='/ABS/NEW/engine.json')
```

`gpu_adf` is the sole authority for native configuration and connections. This version explicitly selects a single chiplet with LRC disabled; unsupported subsets are rejected. `SpaceMatrix.connections` uses the common `adf.Connection`, with five fields: `source`, `source_port`, `destination`, `destination_port`, and `protocol`. For example:

```json
{"source":"component_gpu/cluster[0]/sm","source_port":"request","destination":"component_gpu/icnt","destination_port":"request0","protocol":"transaction.v1"}
```

Endpoints are physical paths after expanding repeat; repeat>1 uses `[i]`. The six types of directed connections are SM→ICNT, ICNT→SM, ICNT→L2, L2→ICNT, L2→DRAM, DRAM→L2. Clusters come with L1/shared; the framework only consumes ports, transactions, and clocks. `compile_topology` rejects missing, multiple, or incorrect connections. Existing unconnected ADFs can be passed to the common `connect_gpu(adf)` to copy and connect; it does not overwrite existing connections or fix unsupported parameters.

`--hardware hardware-async.json` uses the detailed DRAM and four-domain asynchronous clocks from the example. The case exposes the actual hardware JSON; after modification, both sides must be identical. Whether cross-SM/memory pressure forms depends on actual mechanism statistics and cannot be inferred directly from frequency differences. When an interface or engine is missing, stop and retain the reason; do not rename the joint provider and continue execution.

Native runs use bounded timeout, memory, and cycle limits, executing serially according to the recorded CPU budget; the instance tutorial's baseline is at most 600 s and 8 GiB per CPU native subprocess group, the budget includes finish, and building uses only one job. Budgets can be further tightened; both normal completion and failure must wait for and reclaim the entire process group, without unlimited retries. This flow does not recover historically canceled runs or collect new GPU traces.

## Checking with the Common Comparator

Comparison logic belongs to the component package's public interface; the user flow only organizes results and displays reports:

```python
from arch_explorer.components.accelsim.componentization import compare_results
report = compare_results(component_result, oracle_result)
assert report['schema'] == 'arch-explorer.accelsim-component-comparison.v1'
assert report['status'] == 'passed'
```

The comparator first read-only verifies the two complete results and their originals, then validates:

- Exact versions, patch/build identities, configurations, common program/trace, inputs, and mappings on both sides;
- Kernel set and order, overall and per-kernel cycles, retired instructions, and CTAs;
- Declared mechanisms such as cache hits/misses, DRAM reads/writes, interconnect transfers, backpressure, and asynchronous clocks;
- Kernel completion and system_drained; consumer readiness must not be mistaken for physical drain.

Integer counts and completion order require exact consistency; ns uses the same source clock for conversion. Missing metrics, truncation, unknown ISA, or no drain must fail or be explicitly unsupported; do not fill zeros, fit, or pass with broad percentage tolerances.

### Foreground Completion and Physical Drain

The new component-engine's `Evaluation.latency_ns` represents the physical drain moment. The component package calculates it from `final.total_cycles` and the source core clock; user scripts only copy the result. In the results, `details.native.gpu_tot_sim_cycle`, `latency_ns`, `latency_ns_exact` retain the original foreground values; `system_drained_cycles`, `system_drained_latency_ns`, `system_drained_latency_ns_exact` give the physical completion values. The helper displays them separately in `run.json` and marks `latency_semantics=physical_system_drain`.

The comparator retains `foreground_final` before entering the tail, tail `drain_ticks`, `drain_core_cycles`, and `final`. Differences in foreground per-kernel/total and tail/final mechanisms must all pass. `drain_ticks` is the number of additional clock advances; `drain_core_cycles` is the difference in real accumulated core cycles; the two must not be conflated. The tail continues advancing existing physical work, does not add kernels, retired instructions, or CTAs, and does not append cache flushes; when there is a tail, the breakdown lists `phase='physical_system_drain'` separately and cannot be stuffed into the last kernel. The final physical cycles need not equal the per-kernel total.

`active()==false` or process exit 0 alone cannot prove drain. The foreground must complete normally, and real queues, pipelines, responses, and resources must be returned; no progress, truncation, total budget exceeded, or no drain is still a failure. Timeout/memory/cycle budgets cover foreground plus tail and cannot be reset at finish. Read-only replay does not execute finish. Old engine.v1/v2 latency semantics retain the original contract; the new oracle's explicit tail continuation cannot be interpreted as the old runner having already physically drained.

Input/source mismatches throw errors; legal same inputs but different counts return `status='failed'` with differences. The helper saves the complete comparison report and marks the total run as failed. Only when all mapping reports are `passed` is `compared` written in `run.json`. On mismatch, retain both sides' originals, identities, and scope. Do not fabricate success by rewriting request summaries, copying oracle counts, or changing user parameters. If there is no legally reusable real CUDA application trace, report that coverage was not obtained.

The report completely retains `native`, `counter_differences`, `mechanism_differences`, `identity`, `results`, and `evidence`. The ADFs, workloads, mapping sets, and options on both sides must be identical before any native execution; the true binding of underlying source code, inputs, and execution originals is still verified by the common comparator.

## Replay and Result Interpretation

```sh
python workflow.py replay runs/vit --output replay-vit-again.json
archexplorer evaluate runs/vit/candidate/mapping-000/result.json --output replay-components.json
archexplorer evaluate runs/vit/oracle/mapping-000/result.json --output replay-oracle.json
```

Provider result replay should read-only verify the original request, implementation source, and execution receipt, without re-executing native. Save the original paths and files referenced by both sides; prepare new directories after inputs, configurations, or implementations change.

The final delivery retains the common comparison report, both sides' original results, failed/untried items, and reproducible commands. Complete small models, real collected traces, real weights, framework numerical consistency, and device latency accuracy are different scopes and should be stated separately. User agents can consume this flow according to the [run skill](../skills/arch-explorer-run/SKILL.md); component authors' interface requirements are in [component split boundaries](accelsim-componentization.md).
