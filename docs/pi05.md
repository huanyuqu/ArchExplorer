# π0.5 Non-GPU Complete Graph and Execution Boundaries

`WorkloadSpec(kind="pi05")` and `model_specs` preserve the declarative semantics of complete single-device inference: three-way vision, prefix KV, action experts and flow loops, as well as shape, mask, cache, and precision contracts. `examples/workloads/pi05-*.json` only saves workload descriptions; an explicit architecture and mapping are required for execution.

`backend="events"` with `gsm_tiled` supports the complete `openpi.pi05.v1` graph on a single device. The architecture must be explicit non-GPU components, such as a BF16 systolic array, an FP32 vector unit supporting FP32 matrix and vector operations, SRAM, DRAM, and an interconnect network. `applicable` is determined by the actual kernel precision and component capabilities of each operator; BF16 is not treated as FP16, and GPU formulas are not restored because of architecture names or workload names.

The default `dtype="bfloat16"` preserves FP32 initialization weights, one BF16 conversion copy produced on demand, and independent operator precision. SigLIP's QK/softmax still use activation precision and FP32 reduction; Gemma QK/RMS/RoPE and the action/time paths still use FP32 as in the original graph. `dtype="float32"` uses the corresponding FP32 branch. Missing required matrix precision or vector capability is explicitly rejected. Complete graph mapping preserves prefix KV, FP32 scratch, weight liveness, independent requests, output events, and mandatory capacity checks.

If the matrix unit cannot perform result conversion, the mapping writes FP32 accumulation results to explicit DRAM scratch, and the vector unit reads them back and converts to BF16/FP16. Intermediate result liveness, SRAM working set, DRAM/network traffic, and conversion instructions are all accounted for; `explicit_output_casts`, `fp32_matrix_scratch_bytes`, and conversion read/write bytes are reported separately from the fusable path's `fused_output_casts`. This process reuses the generic complete graph and component model and does not introduce π0.5-specific timers. Generic non-GPU multi-device ViT/CLIP mappings reuse the same output plan, allocating temporary results with per-rank local shapes. K-shard partials write FP32 directly, allreduce stays FP32, and conversion happens only once after reduction according to the output type; this path does not stack the old `partial_store` byte compensation. This π0.5 preservation work remains limited to single-device events.

Events latency comes from synthetic systolic/vector parameters declared item by item in the architecture. It does not represent GPU performance, real weight action numerics, robot closed-loop behavior, or calibrated hardware latency. The `noise_seed` in the workload is input semantics and does not serve as a source of device parameters.

GPU ADFs (including Accel-Sim components) continue to reject `gsm_tiled`. The native GPU demo's frozen scope is small ViT/CLIP; π0.5 native Accel-Sim execution and multi-device native GPU/PIM extensions remain unsupported. Backends that do not declare the corresponding `openpi.pi05.v1` contract must reject it and cannot fall back to a single GEMM or fabricate action outputs. Semantic graphs, real weight numeric inference, robot closed-loop behavior, and physical latency accuracy each require separate evidence.
