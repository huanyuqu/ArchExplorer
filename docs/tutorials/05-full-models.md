# 5. New workload → GPU components → mapping → native program simulation

For complete small-model entry points for public compilation, Events/Roofline, layout exploration, and save/restore, see the [ViT public compilation tutorial](../vit-compilation.md) and the [CLIP public dual-tower tutorial](../clip-compilation.md). This page continues to use the native program provider and external engine; existing native results retain their original identity, and new public model configurations or CPU/component results cannot be relabeled as new validation of the old native program.

This demo uses an explicitly reduced complete ViT classification forward pass and a complete CLIP image-text dual-tower forward pass to show how to connect workloads, select mappings, generate native programs, and compare simulation results. ViT's output is classification logits; CLIP includes a vision tower, text tower, projection, normalization, and similarity output. Executing only one attention or one integer kernel does not constitute these two demos.

The dimensions, inputs, numerical references, and generation methods of the quick configurations are reported by the `scope` of `program_demo_specs()` and component artifacts. Small configurations do not represent ViT-B/16 or CLIP ViT-B/32; standard model semantics are preserved in `examples/workloads/vit.json` and `clip.json`, and their native execution capability must be checked separately. Real captures, public traces, and synthetic traces generated by reference execution must each be interpreted according to their own sources. Synthetic reference execution does not prove official framework compilation consistency or physical GPU latency accuracy.

## Prepare installation and external engine

After installing ArchExplorer, first prepare the fixed-version Accel-Sim/GPGPU-Sim binaries, simulation libraries, and engine manifest according to the [engine instructions](../accelsim.md). The manifest references external files; the CUDA runtime cannot replace the simulation library. Native simulation runs on the CPU; preparation and execution do not automatically capture a real GPU or download model weights.

This workflow uses `arch_explorer.simulator.api` and the explicitly selected `accelsim` provider. The component package owns the native mechanism; scenarios are constructed by `archs.accelsim.program_demo_specs`. A build with only single-kernel capability will explicitly report the missing capability; when there is no engine or program capability, it will not switch to prediction formulas. When the backend reports unsupported for operators, ISA, inputs, completeness, or resources, retain the report and stop; do not count it as completed.

## Run from a new directory

Use an output directory that does not yet exist. Replace `/absolute/path/engine.json` below with the actual manifest:

```sh
archexplorer demo prepare --model vit --engine /absolute/path/engine.json --output runs/vit
cat runs/vit/specs.json
cat runs/vit/mapping-000/assessment.json
cat runs/vit/mapping-001/assessment.json
archexplorer demo run runs/vit
cat runs/vit/comparison.json

archexplorer demo prepare --model clip --engine /absolute/path/engine.json --output runs/clip
archexplorer demo run runs/clip
cat runs/clip/comparison.json
```

`prepare` only generates requests and prechecks. `prepared` means execution can be attempted, but there is no successful Evaluation yet; `unsupported` indicates itemized gaps. `run` re-prechecks all requests, calls the native backend, and generates `comparison.json` only if every candidate returns a valid Evaluation. Failures are written to `run.json`, and no successful overall comparison is generated. The output directory and native file paths are saved in this request; the directory and external engine files are retained during replay.

| File | Purpose |
| --- | --- |
| `specs.json` | ADF, complete WorkloadSpec, two MappingSpecs, and scope/source declarations |
| `preparation.json` | Standard objects at prepare time, candidate declarations, and normalized identity associations of the complete public request |
| `adf.json`, `workload.json`, `mappings.json` | View component parameters, workload, and mapping separately |
| `mapping-NNN/request.json` | Public program request, binding workload, components, and actual program |
| `mapping-NNN/assessment.json` | Complete program capability and gap check, without substitute latency |
| `mapping-NNN/program/` | Backend-owned program, reference, trace, and other artifacts, as described by the request |
| `mapping-NNN/result.json` | Native result and complete request, directly replayable |
| `comparison.json` | Complete Evaluation for each candidate: ns, native cycles/counts, sources and scope in backend details |

When comparing, check native cycles, clock sources, actual kernel/instruction coverage, and reference outputs at the same time. The two mappings must be semantically equivalent on the reference and change the real program, partitioning, or execution geometry; different labels are not enough. run first verifies the entire candidate set, preparation records, public specs, and each complete request, then checks support capability; duplicate references (including path aliases), copying the same request, missing/extra/reordered candidates, label rewriting, or replacing requests after preparation will all fail, and the legal subset will not be executed first. The mappings in the comparison come from the verified preparation associations. When changing shapes, ADF, mapping, or requests, re-prepare to a new directory; if an old directory lacks preparation records, it must also be regenerated. Local association records and hashes are used to verify that preparation, and do not authenticate the semantics of the entire directory after arbitrary rewriting, nor replace backend program binding. The second mapping is not guaranteed to be faster. Unknown costs remain null, and host Python wall-clock time is not GPU inference latency. A complete sequential program is processed by the same native execution across kernel/cache states and cannot be summed after per-kernel cold starts.

## View objects, structure, and component mapping with Python

```python
from dataclasses import asdict
from arch_explorer.adf import WorkloadSpec, MappingSpec, from_dict
from arch_explorer.archs.accelsim import program_demo_specs
from arch_explorer.simulator.api import prepare_request, assess_request, evaluate_request
from arch_explorer.workload.full_models import full_model_workload

specs = program_demo_specs("vit")
print(specs["scope"])
workload = WorkloadSpec(**specs["workload"])
adf = from_dict(specs["adf"])
mappings = [MappingSpec(**value) for value in specs["mappings"]]
graph = full_model_workload(workload.kind, workload.params)
print(asdict(graph))  # all tensors, operators, dependencies, and output metadata
print(adf.to_dict())  # public components, parameters, and sources; native field mapping is checked by the component provider

for index, mapping in enumerate(mappings):
    request = prepare_request(adf, workload, mapping,
                              output_dir=f"runs/python-vit-{index}",
                              provider=specs["provider"],
                              options={"engine": "/absolute/path/engine.json"})
    assessment = assess_request(request)
    print(mapping.to_dict(), assessment)
    if not assessment["supported"]:
        raise ValueError(assessment)
    result = evaluate_request(request)
    print(result["evaluation"])  # unified Evaluation.to_dict(), including raw backend details
```

The public demo runner can also be used from Python:

```python
from arch_explorer.demo import prepare_demo, run_demo
prepare_demo("runs/python-demo", model="clip", engine="/absolute/path/engine.json")
comparison = run_demo("runs/python-demo")
```

`python -m arch_explorer.demo prepare ...` is the same as `archexplorer demo prepare ...`; after installing the wheel, it can be invoked from any working directory and does not depend on in-repository tool scripts or a developer Workspace.

## Change one shape while keeping GPU components unchanged

Change the batch of the same small model to 2 and regenerate the request, rather than editing the generated hash or geometry:

```python
import json
from arch_explorer.archs.accelsim import program_demo_specs
specs = program_demo_specs("vit")
specs["workload"]["params"]["batch"] = 2
with open("batch-two.json", "w") as file:
    json.dump(specs, file, indent=2)
```

```sh
archexplorer demo prepare --specs batch-two.json --engine /absolute/path/engine.json --output runs/vit-batch-two
archexplorer demo run runs/vit-batch-two
```

The new inputs and numerical references are owned by the workload/external semantics, and the target execution implementation is regenerated and bound to the program. When the backend does not support the new shape, it explicitly rejects it; this rejection does not count as a successful simulation of the new shape. Extending the same type of workload only changes the external semantics/graph and target execution implementation; the GPU provider, CLI, runner, and physical components do not add model-name branches. For new operators, refer to the [external execution implementation tutorial](../operator-implementations.md), not adding another model kind to the provider. If new operators or instructions are needed, declare support in the module that owns that semantics; unsupported instructions cannot be ignored or given zero latency.

## Change component parameters while keeping the workload unchanged

For example, change the SM core clock to a legal 1500 MHz and explicitly mark it as a comparison scenario:

```python
import json
from arch_explorer.archs.accelsim import program_demo_specs
from arch_explorer.adf import Param, from_dict
specs = program_demo_specs("vit")
adf = from_dict(specs["adf"])
adf.child("cluster").child("sm").params["clock_mhz"] = Param(
    1500, "MHz", "demo sensitivity scenario: 1500 MHz; not a measured device")
specs["adf"] = adf.to_dict()
print(adf.to_dict())
with open("changed-clock.json", "w") as file:
    json.dump(specs, file, indent=2)
```

```sh
archexplorer demo prepare --specs changed-clock.json --engine /absolute/path/engine.json --output runs/vit-clock
archexplorer demo run runs/vit-clock
```

The native configuration compiler is responsible for checking parameter legality and written fields. Check the component map, configuration sources, and native counts in the new results; do not scale old cycles in Python, and do not promise that latency changes monotonically with one parameter.

## Independent replay and failures

```sh
archexplorer evaluate runs/vit/mapping-000/request.json --output runs/vit-first.json
archexplorer evaluate runs/vit/mapping-000/result.json --output runs/vit-replayed.json
```

The new outer schema is `arch-explorer.simulator-request.v1` / `arch-explorer.simulator-result.v1`, binding provider id/version, standard specs, and complete payload. Historical exact schemas are forwarded to the provider's registered handler by the same generic resolver. The [single-kernel example](../accelsim.md) is not evidence of a complete model. Missing engine, timeout, illegal source, missing kernel, incorrect binding, or unknown instruction must fail; do not fill with zeros or reuse historical predictions. This only explains native integration and result review; hardware accuracy, standard model execution, and real weight prediction each require separate evidence.
